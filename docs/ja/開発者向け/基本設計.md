# 基本設計

このドキュメントは、お立ち台Botに新しく参画する開発者向けの入り口です。
**何を作っているのか／なぜそう作るのか／どんな振る舞いを実現するのか**を一通り把握できるよう、コンセプトと設計思想を中心に書いています。
モジュール構成や状態遷移などの実装観点は [アーキテクチャ.md](アーキテクチャ.md) に分離しています。

## このBotは何か

**お立ち台Bot** は、Discordサーバー上でボイスチャンネル（VC）を「共有資源として貸し出す」ためのDiscordボットです。
利用したいメンバーは利用目的をサーバー側に申告してからVCを借り、利用が終われば自動的に返却されます。サーバー管理者は、誰がいつ何のためにVCを使ったかを把握できます。

## 設計の核となる発想

Discord公式の**ステージチャンネル**のアナロジーから出発しています。
ステージチャンネルでは「壇上に上がる人は予め申請する」という非対称な構造によって、発信側と聴衆の役割が自然に分かれます。

お立ち台Botはこの構造を通常のVCに持ち込み、次の前提を敷きます。

1. **VCの利用は「借りる」行為である** — 占有ではなく時限的な貸し出し
2. **借りる前に必ず利用目的を述べる** — 申請とは目的の言語化である
3. **目的を述べないと部屋は割り当てられない** — タイムアウトすれば運営に通知される
4. **利用が終われば自動的に返却される** — 部屋主の退出を、引き継ぎ可否を含めて検知する

「お立ち台」という名前は、VCに入る＝壇上に立つ、というイメージに由来します。

## このBotが解消する摩擦

複数人で1つのDiscordサーバーを共有していると、VC利用に次のような摩擦が生まれます。
お立ち台Botは「目的を聞いてから貸す」という1つの仕掛けでこれらをまとめて吸収します。

- **誰が何のためにそのVCを使っているのか分からない** — 運営にも他メンバーにも見えない
- **空いているVCを判別する手段がない** — チャンネル名や暗黙ルールに頼ると徐々に崩壊する
- **無断占有や荒らしの発見が遅れる** — 「なんとなくそこにいる」状態を検知できない

権限管理だけで同じことを実現しようとすると、運営の人手と細かいルール文書化が必要になります。

## 登場人物

| ロール | 主にできること |
|---|---|
| **サーバー利用者** | レンタル申請を行い、割り当てられた部屋を利用する |
| **部屋主** | 申請者から派生するロール。VCを抜けると部屋が解放、または他参加者へ引き継がれる |
| **サーバー管理者** | 貸し出す部屋の登録、通報先・レンタルボタン設置先の設定、表示言語などの設定 |
| **Bot運用者** | このBot自体をホストし、複数サーバーへ提供する側 |

サーバー管理者は通報を受け取る運営の役割を兼ねることが多いですが、通報先チャンネルを別途指定することで、管理権限を持たない運営スタッフへ通知を回すこともできます。

## 中核ユースケース

### 1. 申請から利用まで

利用者は次のいずれかでレンタル申請を始められます。

- 管理者が用意したレンタルボタンを押す
- `/rent` コマンドを実行する
- 参加者のいないVCに入る

3経路あるのは、それぞれ**「目に入った時」「思いついた時」「とにかくVCを使いたい時」**という異なる動線をカバーするためです。とくにVC参加によるトリガーは、Botを意識しない自然な体験を実現する要となっています。

申請が始まると、Botが利用目的を尋ね、入力されると空いている部屋が1つ割り当てられます。

### 2. 自動返却と引き継ぎ

部屋主がVCから退出すると、Botが状況を判定して部屋を解放します。
他の参加者が残っている場合は、引き継ぎ確認を経て解放するかを決めます。これにより「部屋主が一瞬抜けただけで全員の利用が終わる」事故を防ぎます。

### 3. 異常時の通報

利用目的が一定時間内（既定10分）に入力されない場合、Botは事前登録された通報先チャンネルへ通知します。
逆に、入力前にVCを抜けた場合は単なる気変わりとみなし、通報しません。**ノイズを増やさない**ことを優先する設計判断です。

## 設計原則

### コマンドより自然な体験を優先する

利用者がBotを「使っている」と意識せずに済むことを目指します。
スラッシュコマンドは補助手段で、最も自然な動線は「VCに入る」ことです。コマンドの完成度よりイベント駆動の動線整備を優先します。

### サーバーごとに振る舞いをカスタマイズできる

部屋構成・通報先・レンタルボタン設置先・表示言語はサーバー単位で設定でき、Bot運用者の介入なしにサーバー管理者が完結できます。
このBotは1インスタンスで複数サーバーをホストする前提です。

### サーバー間の情報は混じらない

複数サーバーが同じBotインスタンスを共有しても、あるサーバーの部屋・レンタル状態・設定が別サーバーから見える・操作できることがあってはいけません。
これはアプリケーション層のチェックではなくデータベース層で強制します（実装は[アーキテクチャ.md](アーキテクチャ.md)参照）。

### 言語に依存しない

利用者向けに表示するメッセージは多言語化されており、利用者・サーバー・Botのいずれかの設定から表示言語が決まります。日本語・英語の追加運用だけでなく、将来の言語追加も特定言語の前提なく行えるようにします。

### 永続化された状態を信頼の起点にする

レンタル状態は応答性のためメモリ上にも保持しますが、メモリ上の状態は補助に過ぎません。
プロセス再起動・障害でメモリが失われても、DBの永続状態から正しい状態を再構築できることを設計の前提とします。

## スコープ外

設計を太らせないために、以下は明示的に対象外とします。

- **VC内の音声処理** — 録音・音声分析・読み上げなどは扱わない
- **チャットモデレーション** — 発言内容の自動検閲は行わない
- **予約システム** — 「明日20時から借りる」のような未来予約は持たない
- **1人による複数部屋の同時レンタル** — 1人＝1部屋を原則とする

これらは将来検討する余地はありますが、現在の基本設計には含めません。
