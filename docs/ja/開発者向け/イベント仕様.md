# イベント仕様

お立ち台Botが反応する**ゲートウェイイベント**（Discordから受信するイベント）と**内部イベント**（タイマー・スケジューラ起源のイベント）を一覧します。
入口は `src/discord/events/dispatcher.rs` の `dispatch` 関数で、ここから各サブハンドラに振り分けられます。

## 受信するゲートウェイイベント

`dispatch()` で振り分け対象となっているのは以下の4種類です。それ以外のGatewayイベントは無視します。

| イベント | ハンドラ | 主目的 |
|---|---|---|
| `Ready` | `events::guild::handle_ready` | 起動完了の検知とスラッシュコマンドのグローバル登録 |
| `GuildCreate` | `events::guild::handle_guild_create` | サーバー参加の検知（現状はログのみ） |
| `InteractionCreate` | `events::interaction::handle` | コマンド・ボタン・モーダル送信の処理 |
| `VoiceStateUpdate` | `events::voice_state::handle` | VC入退出によるレンタル開始・終了・引き継ぎ |

---

### Ready

| 項目 | 内容 |
|---|---|
| 受信契機 | Discord Gateway接続が完了したとき |
| 処理 | スラッシュコマンドをグローバル登録（`commands::register::register_global_commands`） |
| 副作用 | Discord側のコマンドツリーが更新される |

ギルド限定登録ではなくグローバル登録のため、新コマンドの反映には最大1時間程度かかる場合があります。

### GuildCreate

| 項目 | 内容 |
|---|---|
| 受信契機 | Botがサーバーに参加した、もしくは起動時に既参加サーバーを通知された |
| 処理 | 現状は `tracing::debug!` でログ出力のみ |
| 副作用 | なし |

将来的にサーバー初期化処理を入れる余地のあるフックです。

### InteractionCreate

サーバー外（DM）のインタラクションは無視します（`guild_id` が `None` のものは早期 return）。
3種類のサブタイプを `interaction.kind` で分岐します。

#### ApplicationCommand（スラッシュコマンド）

| 項目 | 内容 |
|---|---|
| 受信契機 | ユーザーがスラッシュコマンドを送信 |
| 権限チェック | コマンド名が管理系（`register_*` / `delete_room`）の場合、`ADMINISTRATOR` または `MANAGE_GUILD` 権限を要求 |
| 言語解決 | `language::resolve_language(&state, guild_id, interaction.locale)` |
| ルーティング | `commands::admin::*::handle` または `commands::user::*::handle` を `data.name` で呼び分け |
| 応答 | 通常は `ChannelMessageWithSource`、権限拒否時のみ ephemeral |

各コマンドの詳細は [コマンド仕様.md](コマンド仕様.md) を参照。

#### MessageComponent（ボタン押下）

`custom_id` の形式で分岐します。

| custom_id | 発生源 | 処理 |
|---|---|---|
| `rental_start` | レンタルボタンチャンネルに常設されたボタン | `/rent` 相当のフロー（`commands::user::rent::handle`）を実行 |
| `rental_start:{session_id}:{room_id}` | VC参加時にBotが投稿する個別ボタン | 対象セッションの保留中ホスト本人なら、その部屋の質問プリセットでモーダルを返す |
| `handoff_accept:{session_id}:{room_id}` | 部屋主退出時にBotが投稿する引き継ぎボタン | `DeferredUpdateMessage` を返したのち `handoff::accept_handoff` を実行 |

`rental_start:{session_id}:{room_id}` は本人検証として `RentalState::AwaitingPurpose` の `host_user_id` と一致するかを `is_pending_rental_host` で確認し、不一致なら ephemeral でエラーを返します。

#### ModalSubmit（モーダル送信）

| custom_id | 処理 |
|---|---|
| `purpose_modal:{session_id}:{room_id}` | `purpose_text` を取り出し、`rental::flow::submit_purpose` で利用目的を保存しタイマーを停止して `Active` 状態へ遷移 |

応答は ephemeral で、割り当て確定メッセージを返します。

---

### VoiceStateUpdate

ユーザーがVCに入室・退室・移動したときに発火します。
`event.channel_id` が `Some` なら入室／移動先、`None` なら退室です。
ハンドラは `previous_vc`（状態マップから引いた現在の在室VC）を参照して**移動を「退出 → 入室」に分解**してから処理します。

#### 入室（handle_join）

| 条件 | 動作 |
|---|---|
| 入室先のVCが `rooms` に登録されていない | 何もしない |
| 状態マップに `(guild_id, vc_id)` の既存エントリがある | レンタル進行中とみなしスキップ |
| それ以外 | レンタル開始（`rental::flow::start_rental`） |

`start_rental` の戻り値で分岐：

- `AwaitingQuestions` — 利用目的入力モーダル用ボタン（`rental_start:{session_id}:{room_id}`）付きメッセージを「VC付属チャット」または「登録済みテキストチャンネル」に投稿。投稿失敗時は `release_rental` で巻き戻し
- `Assigned` — 質問プリセットがない部屋の場合に発生。VC参加だけで `Active` 化（メッセージ投稿はなし）
- `AlreadyRenting` / `NoAvailableRooms` — VCトリガー時はメッセージを出さない（コマンド経路の場合のみ ephemeral 応答）

通知先チャンネルの解決は `prompt_channel_id(text_channel_id, voice_channel_id)`：
- 部屋に `text_channel_id` が登録されていればそのテキストチャンネル
- なければVC付属のテキストチャット

#### 退室（handle_leave）

状態マップ `(guild_id, vc_id)` の現在状態と退室ユーザーの照合結果で分岐します。

| 現在状態と一致 | アクション | 動作 |
|---|---|---|
| `AwaitingPurpose` のホスト本人 | `CancelPending` | `release_rental` でセッション解放・状態マップから除去（通報は出さない） |
| `Active` のホスト本人 | `StartHandoff` | `handoff::initiate_handoff` で引き継ぎ確認メッセージを投稿し、状態を `PendingHandoff` へ |
| 上記以外（ホスト以外の参加者退出など） | `Ignore` | 何もしない |

## 内部イベント（タイマー）

レンタル進行に伴ってBotが起動する2種類のタイマーです。Tokioタスクとしてspawnされ、`JoinHandle` を `RentalStateEntry` 内に保持します。状態が進めば `abort_timeout()` でキャンセルされます。

### 利用目的タイムアウト（既定10分）

| 項目 | 内容 |
|---|---|
| spawn元 | `rental::timeout::spawn_purpose_timeout` |
| トリガー | `start_rental` が `AwaitingPurpose` セッションを作成したとき |
| 期間 | `facade::rental::PURPOSE_TIMEOUT_MINUTES` 分（既定10分） |
| 発火時の動作 | セッションを `released` に更新／`scheduled_tasks` を processed に更新／部屋を空き状態に戻す／状態マップから除去／登録済みなら通報チャンネルに通知 |
| キャンセル契機 | 利用目的の送信完了・本人のVC退出・引き継ぎ移行 |

セッション作成時に `scheduled_tasks` にも同じ期限が永続化されているため、Bot再起動時は `restore_pending_timeouts` が未処理タスクを再spawnし、メモリ消失後も期限を担保します。

### 引き継ぎタイムアウト（300秒固定）

| 項目 | 内容 |
|---|---|
| spawn元 | `rental::timeout::spawn_handoff_timeout` |
| トリガー | `handoff::initiate_handoff`（部屋主の `Active` セッションからの退室）|
| 期間 | `handoff::HANDOFF_TIMEOUT_SECS`（300秒） |
| 発火時の動作 | セッションを `released` に更新／部屋を空き状態に戻す／状態マップから除去 |
| キャンセル契機 | 引き継ぎボタン押下（`handoff_accept`） |

引き継ぎタイムアウト分は `scheduled_tasks` に永続化していないため、再起動時はメモリ上の状態のみで管理されます（DBの `pending_handoff` セッションは別途人手または将来の復元処理で扱う想定）。

---

## エラー処理

`dispatch()` はサブハンドラの `BotResult` を受けて、`Err` の場合は `tracing::error!` でログ出力し処理を継続します。
個々のイベント処理が失敗しても次のイベントは受信され続けるため、一過性の失敗がBot全体を止めることはありません。
